# protein_web — Telegram Mini App «Контроль калорий»

Фронтенд мини-аппа для бота [protein_counter](https://github.com/SanyCska/protein_counter):
дневник питания, нормы и микронутриенты, физнагрузка, отчёты и графики прогресса.

Vite + React + TypeScript. Дизайн — система **Nocturne** (тёмная тема) из дизайн-хендофа;
токены перенесены в `src/styles/tokens.css`, хардкодить хексы нельзя.

## Запуск

Сначала поднимите API (см. README бота), затем:

```bash
npm install && npm run dev
```

Vite проксирует `/api` на `http://127.0.0.1:8000`. Вне Telegram приложение работает
в дев-режиме: вместо подписи initData шлётся заголовок `X-Dev-User-Id`, вверху видна плашка
«Режим разработки». Сервер принимает этот заголовок только при `APP_ENV=dev`.

```bash
npm run build      # сборка в dist/
npm run test       # юнит-тесты
npm run typecheck  # проверка типов
```

Переменные (`.env.local`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `VITE_API_BASE` | `/api` | база API; в проде — если фронт и API на разных доменах |
| `VITE_API_PROXY` | `http://127.0.0.1:8000` | куда Vite проксирует `/api` в деве |
| `VITE_DEV_USER_ID` | `1` | какой пользователь подставляется вне Telegram |

## Экраны

**Дневник** — полоса дней недели, кольца КБЖУ, лента событий за день (еда, тренировки,
добавки), кнопки добавления.

**Отчёт** — день / неделя / месяц: КБЖУ и 25 микронутриентов против нормы, фильтр
«Дефицит / Норма+ / Все», рекомендации «что добрать», энергетический итог.

**Прогресс** — четыре графика (калории, белок, расход на нагрузке, баланс к норме) и
плитки статистики со сравнением с прошлым периодом. Расход на нагрузке — отдельный график:
в бюджет калорий он не входит и норму не поднимает.

**Профиль** — параметры тела, расчётная норма, добавки, шаблоны нагрузки (тап добавляет
тренировку в день одним действием). Норму можно задать руками прямо на её карточке:
«Задать свою» открывает поле, «Вернуть расчётную» возвращает формулу. Своя норма
заменяет только калории — белок и жиры остаются привязаны к весу, разницу забирают
углеводы.

Плюс четыре нижних шита: добавление блюда (ИИ-разбор / поиск / вручную), деталь блюда,
физнагрузка, добавка.

Запись дня правится целиком: название, время, тип приёма. У блюда с разбором — состав:
ингредиент переименовывается, граммовка двигается степпером, лишний убирается, а КБЖУ
и витамины пересчитываются из состава. У записи без разбора — сами КБЖУ, порция с единицей
и микронутриенты. На сервер уходят только изменённые поля.

Ручной ввод разделён на две части: сверху «данные указаны на» — порция с упаковки или
100 г, и КБЖУ относятся именно к ней; снизу «съел сейчас» — сколько съедено на самом деле.
В день попадает пересчитанное, а в справочник продуктов, если отметить галочку, ложится
порция-основа. То же и в поиске: у продукта с известной порцией сначала спрашивается
съеденное количество.

Фото работает в трёх местах: снимок тарелки в ИИ-разборе, снимок упаковки в ручном режиме
(заполняет форму по таблице пищевой ценности) и снимок банки в шите добавок — оттуда
приезжает сразу несколько веществ, каждое отдельной строкой, и строки можно дописать
руками. Дозы остаются как на этикетке, а два поля рядом говорят, какая их доля идёт
в отчёт: «доза на этикетке» — на сколько таблеток посчитана таблица, «принимаю» — сколько
их пьёте. Таблица на три таблетки при приёме одной даёт треть доз. Менять это можно
когда угодно: доли хранятся вместе с дозами, а не выжигаются в них.

Банка сохраняется под одним названием — его вводит пользователь. В списке добавок и в
ленте дня она занимает одну строку с составом внутри, а в отчёт по микронутриентам
попадает каждым веществом отдельно. Тап по названию открывает ту же форму на правку:
дозу и единицу с этикетки ИИ иногда читает неверно, и поправить их надо уметь, не заводя
банку заново. Порция считается в граммах или миллилитрах: единица — подпись к числу,
пересчёта между ними нет. Из детали блюда запись сохраняется в свои продукты с любой
порцией — состав и микронутриенты пересчитываются на неё.

## Деплой

Пуш в `main` запускает workflow: тесты и типы → Docker-образ со статикой (Vite + nginx)
в GHCR → SSH на сервер, где перезапускается только контейнер `web`.

Compose-стек и `.env` живут на сервере и приезжают из репозитория бота
[protein_counter](https://github.com/SanyCska/protein_counter) — он должен быть
задеплоен хотя бы раз, иначе `docker compose pull web` не найдёт сервис.
TLS и маршрут `/api` держит Caddy из того же стека, поэтому фронт и API
на одном origin и `VITE_API_BASE` в проде менять не нужно.

Секреты репозитория (Settings → Secrets and variables → Actions) — те же значения,
что у бэкенда: `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `DEPLOY_PATH`
и `SSH_PORT`, если SSH не на 22. Ключей приложения фронту не нужно:
пользователь определяется подписью Telegram, которую проверяет API.

Образ можно собрать и локально:

```bash
docker build -t protein-web . && docker run --rm -p 8080:80 protein-web
```

## Структура

```
src/
  api/         клиент, типы, react-query хуки, обёртка Telegram SDK
  app/         оболочка: хедер, таб-бар, UI-состояние (zustand)
  components/  примитивы: карточки, сегменты, бары, степперы, шиты
  lib/         форматирование дат и чисел, расчёты нутриентов
  screens/     Diary, Report, Progress, Profile
  sheets/      четыре нижних шита + хост
  styles/      токены Nocturne и базовые стили
```

## Решения, которые стоит знать

**Графики нарисованы руками** на div/SVG, без библиотеки. Дизайн описывает их попиксельно —
библиотека графиков дала бы меньше контроля и больше веса.

**Итоги блюда пересчитываются локально.** Когда пользователь двигает граммовку в шите,
`totalsFromItems` повторяет серверную формулу, чтобы цифры менялись мгновенно; сервер
пересчитывает их заново при сохранении и остаётся источником истины.

**Любая мутация сбрасывает весь серверный кеш**, кроме справочников. Правка блюда меняет
и ленту дня, и отчёт, и графики — точечная инвалидация здесь легко разъезжается с реальностью.

**Скролл запоминается по табам** — общий контейнер иначе открывает новый таб в середине
чужого экрана.

## Чего пока нет

- **Голосовой ввод** в шите добавления. В макете кнопка есть, но распознавания речи на
  бэкенде нет — кнопка убрана, чтобы не обещать несуществующее.
- **Внешняя база продуктов.** Поиск идёт по своим сохранённым продуктам; точка расширения
  оставлена в `api/routers/products.py` на стороне бэкенда.
- **Кнопка «Список покупок»** в карточке рекомендаций: сами источники продуктов уже
  показываются текстом под каждым дефицитом.
